# Working on EvoRag

The orchestrator owns interfaces, scope, integration and acceptance. Before editing, inspect the worktree and its tracked, staged and untracked changes. Preserve owner edits and deletions. Use an isolated worktree for parallel edits when it can represent the intended baseline safely.

Assign core contracts and algorithms to engineering, independent tests and edge-case review to quality/security, and packaging, documentation and CI to infrastructure. Give each session an explicit file set. Read-only design or review assignments can share a checkout. Verify the available CLI model identifiers before delegating and record actual sessions and limitations.

Use typed Python, frozen boundary contracts, explicit dependencies and deterministic tests. Add implementations as their milestone needs them. Use the standard library first. Pretrained models sit behind HTTP provider boundaries. Keep algorithms owned by EvoRag. Keep credentials, local documents and model responses out of source control and logs.

For each task, define its acceptance test, implement the smallest complete change, request independent review, resolve findings and run the checks in [DEVELOPMENT.md](docs/DEVELOPMENT.md). Record actual results and open issues in [PROJECT_STATE.md](docs/PROJECT_STATE.md). The owner approves pushes, destructive Git operations and the start of the next milestone.
